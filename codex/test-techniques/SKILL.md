# Test Techniques

「ちゃんとテストして」を、具体的な技法名と対象に分解してから実行する。技法の一覧は [references/catalog.md](references/catalog.md)。全部を適用せず、壊れると困る所に効くものを少数選ぶ。

## 1. 対象とリスクを把握する

- 変更内容、主要な利用の流れ、入力の種類（数値・文字列・日付・ファイル）、状態（ログイン、決済、オフライン）、外部依存（API、DB、決済、通知）を読む。
- 既存のテスト基盤（フレームワーク、実行コマンド、CI、フィクスチャ）を確認し、それに合わせる。新しいテスト基盤は依頼がない限り入れない。
- プロジェクトの `CLAUDE.md` / `AGENTS.md` にあるビルド先・結果の置き場所・同時実行数などのルールに従う。

## 2. 技法を選ぶ

症状やリスクから選ぶ。迷ったら下の表から2〜5個に絞り、選んだ理由を1行ずつ書く。

| 気になること | まず使う技法 |
| --- | --- |
| 上限・下限ちょうどの値で壊れる | 境界値分析（3値境界値） |
| テストケースが多すぎる | 同値分割、ペアワイズ法 |
| 条件の組み合わせで結果が変わる | デシジョンテーブル、原因結果グラフ |
| 画面や注文などの状態が切り替わる | 状態遷移テスト（必要ならNスイッチ） |
| 直したら別の所が壊れた | 回帰テスト、特性テスト（直す前の挙動を記録） |
| 主要な流れが通るか不安 | スモークテスト、E2E（ユースケースの基本と例外） |
| 入力の書式（メール・日付・電話番号） | シンタックステスト、異常系テスト |
| 同時操作でデータが壊れる | 並行性テスト |
| 人が増えると遅い・止まる | 負荷・スパイク・ストレステスト |
| 見た目の崩れ | ビジュアル回帰、クロスブラウザ、実機、ローカライズ |
| 誰でも使えるか | アクセシビリティ（WCAG、コントラスト比） |
| 攻撃されないか | 脆弱性診断、ファジング（自分の管理する環境のみ） |
| テスト自体が甘い | カバレッジ計測、ミューテーションテスト |
| 正解がわからない処理（検索、AI、変換） | メタモルフィックテスト、プロパティベーステスト |
| たまに落ちるテスト | フレーキーテストの原因調査 |

## 3. テストケースを具体化する

- 技法ごとに、入力値・前提・操作・期待結果を表にする（例: 境界値分析なら「最小−1、最小、最大、最大+1」）。期待結果は仕様・既存の挙動・ユーザーの指示から取り、推測で決めた所は明記する。
- 自動化できるものは既存のフレームワークでコード化する（準備・実行・確認の3段に分ける、パラメータ化テストで値違いをまとめる、外部サービスはモック/スタブ/フェイクに置き換える）。
- 手動でしか確かめられないもの（実機の触り心地、ユーザビリティ）は、手順と確認項目のチェックリストにする。

## 4. 実行と報告

- 実行して結果を確認する。失敗したテストは、実装のバグか、テストの誤りか、仕様の不明点かを切り分ける。
- 報告には、選んだ技法と理由、追加・変更したテスト、実行コマンドと結果（通過/失敗の数）、見つかった不具合、実施していない技法とその理由を書く。実行していないものを「確認済み」と書かない。

## 安全

- 負荷・ストレス・スパイク・カオス・障害注入・ペネトレーション・ファジングは、ユーザーが管理するローカル環境かテスト環境だけで行う。本番環境や第三者のサービスに向けて実行しない。本番相当の環境に向ける場合は、対象と規模を伝えてから行う。
- テストで本物の決済・メール送信・外部APIへの書き込みが起きないよう、テスト用のキーやモックを使う。
- 実データや個人情報をフィクスチャに入れない。
