# 宿モックアップ 3案生成

営業前の仮説検証用に、小規模宿の「公式サイトがあった場合」のモックアップを3案作る。事実未確認の情報・料金・空室・受賞歴・口コミ・地図・連絡先の捏造は全工程で禁止。未確認の項目は「未確認」と明記する。

デザイン・情報設計・実装・画像の取扱いの全要件は [requirements.md](requirements.md) にある。着手前に読む。

## 手順

### 1. 入力の確定

引数は次のどの形でも受け付け、[input-template.md](input-template.md) の項目に正規化する。

- **入力ブロック直貼り**: そのまま項目として読み取る。
- **リサーチファイルのパス**（.md / .docx / .xlsx / .txt 等、複数可）: ファイルを読み（xlsx・docx は python 等で抽出）、記載の事実を項目に振り分ける。対象宿の行・節だけを使い、他の宿の情報を混ぜない。ファイル中の提案仮説・改善案は「このサイトで解くべき仮説」に、テイスト・売り方への言及は「人間の方針」に写す。事実と仮説を混同しない。
- **宿名＋断片情報**: 分かる範囲で項目に振り分ける。

続けて:

- ファイル由来の情報も推測で補完しない。根拠が引けない項目は「未確認」とする。
- `# 宿の特徴やテイスト（人間の方針）` ブロックは最優先の設計指示。人間にしか見いだせないアピールポイントがここに入る。3案すべてに反映する。
- 宿名も所在地も特定できない場合のみユーザーに確認する。
- `assets/reference/` と `asset-manifest.json` の有無を確認する。無ければ requirements.md「画像の取扱い」に従い、対象宿の公開掲載ページ（Airbnb等）から写真を保存して作る（画像生成は使わない。トリミング可・改変不可・出所記録必須）。取得できない画像の箇所だけ「撮影指示つきプレースホルダー」にする。
- 実写素材を全点一覧化し、コンタクトシートまたは個別表示で内容を確認する。各写真を「ヒーロー・情景・客室・細部・設備・不採用」に分類し、3案ごとの配置計画を作る。使用可能な写真が15枚以下なら、原則として3案それぞれで全点使う。16枚以上なら各案12枚以上を使い、3案全体では全点を使う。不採用は品質・重複・権利・内容不明などの理由を `asset-manifest.json` と解説資料に記録する。
- 公式Instagram/FacebookのアカウントURL、表示候補の投稿URL・投稿日・確認日を確定する。公式と確認できないアカウントや投稿は使わず「未確認」とする。直近の投稿が古い場合は無理に埋め込まず、requirements.md「SNSの取扱い」に従う。
- SNSが未確認・休眠中でも安心材料が空にならないよう、Airbnb・Booking.com等の対象宿ページから、評価、レビュー件数、カテゴリ別評価、短いレビュー要約、確認日を取得する。転載せず、媒体名・件数・確認日・掲載ページURLを必ず残す。複数媒体の数値を合算しない。
- Airbnb等の主掲載ページを「宿情報台帳」として読み、宿名、住所、定員、寝室・寝具・浴室、設備、駐車場、規則、チェックイン/アウト、許可番号、ホスト情報、周辺施設、アクセス、レビュー、掲載上の注意を可能な限り全件拾う。表示しない項目も、理由を解説資料へ残す。
- 正確な住所と公開可否を確認し、Google Maps Embed APIを使えるかを判定する。APIキー未設定時にも住所・道順・Google Maps検索リンクが読めるフォールバックを設計する。
- 表示言語を `ja` / `en` / `zh-CN` / `zh-TW` / `ko` を基本に、対象地域の訪日客構成から少なくとも1言語を追加して確定する。サイトの翻訳言語と、運営者が実際に応対できる言語を分けて記録する。
- 完了条件: input-template.md の全項目が「値」か「未確認」で確定し、全実写素材の分類・3案別配置・不採用理由、宿情報台帳、レビュー出典、地図方式、表示言語が確定している。

### 2. 批評的設計判断（3案共通・1回だけ）

requirements.md の「批評的設計判断」4点を日本語で出す。

完了条件: 約束（15〜25字）・伝わりにくい価値3点・セクション対応表・新設/改善切替の判断、の4点が揃っている。

### 3. トンマナ3候補（宿の個性から）

requirements.md の「デザイン要件（宿の品格）」は全案共通のレジスタとして固定する。そのうえで、宿の実在の要素（例: 蓮池、果実、庭木、土壁、建具、海、雪）から由来の異なる **トンマナ候補を3つ** 作る。各候補の項目: 候補名、由来（宿の何から取ったか）、地色、墨、アクセント1色、写真トーン。

- 3候補は並べて一目で違いが分かること。ただしすべて品格レジスタ（明朝基調・罫線・余白・低彩度）の内側に収める。
- requirements.md の参照サイトから正解ラベルを2〜3件選び、可能なら実際に見て格を合わせる（写真・文章・ロゴの転用はしない）。
- 完了条件: 由来の異なる3候補が揃い、それぞれが宿の実在要素に根拠を持つ。

### 4. 3案の方向づけ（トーン×レイアウト）

各案 = トンマナ候補1つ + 異なる情報設計・レイアウト。ブリーフの項目: 案名、割り当てたトンマナ候補、約束の解釈、セクションの順序と粒度、レイアウト戦略（例: 章立て・時間軸・空間軸、縦書き・横組み、写真主導・文字主導）。

- 3案はトーンでもレイアウトでも互いに異なること。オーナーが「色・空気」と「構成」の両方を見比べられる状態が納品物である。
- 完了条件: 3案を並べたときトーンの違いが一目で分かり、構成も明確に異なり、かつこの宿以外に使い回せる案が1つも無い。

### 5. 実装

- デザインの規範は requirements.md のデザイン要件のみ。汎用のWebデザインスキル（design-taste-frontend 等）は読み込まない。スタートアップLPの文法（ピル型ボタン・影付きカード・ホバー物理）が混入し「AIっぽく」なった経緯がある。
- 目に見える文章はすべて requirements.md の「文章の声（オーナーの声）」で書く。
- 各案を `mockups/<宿のスラッグ>/an1/index.html`（an2・an3 も同様）として、単体でブラウザに開ける完全なHTMLに実装する。出力先の基点は `ホテル広告事業/` ディレクトリ、見つからなければカレント直下。
- 写真は同じ汎用ギャラリーを3案へ複製せず、各案の時間軸・季節軸・空間軸などに沿って置き分ける。同じ案で同じ写真を繰り返すより、異なる写真の掲載率を優先する。季節・時刻・設備が確認できない写真を、その事実の証拠として使わない。
- 実装後、`asset-manifest.json` のファイル一覧と各HTMLの画像参照を機械的に照合し、案ごとの使用点数・未使用ファイル・画像欠けを確認する。
- 完了条件: 3つの index.html がそれぞれ requirements.md の必須情報設計9セクションと実装要件を満たし、実写素材の掲載率が手順1の基準を満たす。確認済みSNS、または出典付き外部レビューの少なくとも一方で運営実態を示し、宿情報・住所・アクセス・駐車場・地図導線・多言語UIを実装する。目に見える全文章は「オーナーがお客さんの前でそのまま口にできる」言葉とし、内部向け注記を含めない。省略・「以下同様」は不可。

### 6. PDF化と解説資料

オーナーへの提示はPDFが基本（HTMLは商談の場で実際にスクロールして見せる用）。

- **各案のPDF**: 各 index.html を headless Chrome（`--headless=new --virtual-time-budget=8000 --no-pdf-header-footer --print-to-pdf=...`）で `mockups/<宿スラッグ>/an1.pdf`（an2・an3 も同様）に変換する。変換後、先頭数ページを開いて白紙セクション・画像欠けが無いことを確認する（印刷用CSSは実装要件参照）。
- **解説資料**: requirements.md「解説資料（proposal-guide）」に従い、`mockups/<宿スラッグ>/proposal-guide.pdf` を作る（3案の狙い・差し替え指示・カスタマイズ案・事実確認リスト・画像出所・レビュー/SNSの更新方法・宿情報台帳・地図設定・翻訳運用）。

完了条件: an1〜an3.pdf と proposal-guide.pdf が存在し、各案PDFに白紙・欠けが無く、事実確認リストがページ上の全ての仮表示・公開情報由来の記述をカバーしている。

### 7. 納品

以下をまとめて出力して終了する。

1. 批評的設計判断（手順2の内容）
2. トンマナ3候補（候補名・由来・配色）と選んだ正解ラベル
3. 3案の比較表: 案名・トンマナ候補・構成とレイアウトの違い・向くオーナー像
4. 各 index.html・an1〜an3.pdf・proposal-guide.pdf のパス
5. requirements.md 末尾の「公開前に人間が確認する項目」チェックリスト
